# gamescope and GameMode support in DZL

Date: 2026-07-26
Status: approved, ready for an implementation plan

## Background

DZL launches the game with `steam -applaunch 221100 ...` (`src-tauri/src/commands/join.rs`,
`spawn_steam` and `build_launch_command`). Steam applies the app's stored Launch
Options to that command, so a `%command%` wrapper configured in Steam already
takes effect on a DZL launch.

This was verified from `~/.steam/steam/logs/console-linux.txt` rather than from
documentation. Two DZL launches on 2026-07-25 (lines 11162 and 13529, 00:55:36
and 12:16:19) passed DayZ flags only, with no wrapper tokens, yet both windows
contain `[gamescope] ...` and `gamemodeauto:` output and the only game running in
each window is `gameID 221100`. The wrapper from `localconfig.vdf` ran.

Two facts follow, and they shape this design:

1. DZL cannot wrap the game itself in the normal case. When Steam is already
   running, `steam -applaunch` hands the request to the running client over IPC
   and the game inherits that client's environment, not DZL's. A wrapper has to
   come from the Steam side, through `%command%`.
2. `localconfig.vdf` is only safely writable while Steam is closed. Steam holds
   the config in memory and writes it back on exit, clobbering outside edits.

A related trap was found in the same log. At 22:20:46 (line 16395) a DZL launch
carried `'gamemoderun' 'gamescope' '-W' '2560' ... '--force-grab-cursor' '--'
'%command%'` as literal DayZ arguments, because the wrapper string had been
pasted into DZL's **Extra arguments** field. DayZ ignores them. DZL accepts that
input with no warning today, which is a large part of why the feature looks
broken from the outside.

## Goal

DZL owns the wrapper for DayZ, so a user never has to open Steam's game
properties: toggles for GameMode and gamescope, the common gamescope settings,
and a free-form field for anything else.

## Non-goals

- Launching the game without the Steam client (DZL taking on Proton, the Steam
  runtime and BattlEye). Rejected as a large, risky lift.
- Registering DZL as a Steam compatibility tool. More machinery than this needs,
  and it takes over Proton version selection.
- Rewriting Steam's Launch Options on every settings change. Each change would
  need Steam closed and restarted.
- A MangoHud toggle. Not installed on the reference machine and not asked for.
  Anyone who wants it can add `MANGOHUD=1` in the environment rows, which is
  enough for a Vulkan game.

## Architecture

Two moving parts, separated so that only one of them ever touches Steam.

### The hook (rare, guarded)

Steam's `apps/221100/LaunchOptions` is set once, to:

```
<data dir>/dzl-wrap.sh %command%
```

where `<data dir>` is DZL's own data directory, `~/.local/share/com.dzl.launcher`
on the reference machine.

A new module `src-tauri/src/steam_vdf.rs` performs the edit. It is pure Rust with
no Tauri dependency and no new crate: a surgical text edit rather than a
parse-and-reserialise of the whole 1 MB file. It locates
`UserLocalConfigStore/Software/Valve/Steam/apps/221100` (verified as the real key
path on the reference machine, `localconfig.vdf` line 320) and then either
replaces the `LaunchOptions` line, inserts one into the existing app block, or
inserts the whole app block when DayZ has never been launched on that account.
Everything else in the file comes out byte for byte identical.

Account selection reads `MostRecent` from `~/.steam/steam/config/loginusers.vdf`,
falling back to the newest `localconfig.vdf` mtime. Settings displays which
account was hooked so a multi-account user can confirm it went to the right one.

### The wrapper script (frequent, free)

`dzl-wrap.sh` is DZL's own file, regenerated in full on every settings save. It
holds literal flags, so no JSON parsing happens in shell. For the reference
configuration it comes out as:

```sh
#!/bin/sh
# Generated by DZL. Do not edit; change the launcher's settings instead.
command -v gamescope >/dev/null 2>&1 || exec "$@"
export LD_PRELOAD=""
exec gamemoderun gamescope -W 2560 -H 1440 -f -r 180 --force-grab-cursor -- "$@"
```

Toggles therefore apply on the next launch with no Steam restart, no Steam config
write and no launcher restart. With everything off the script degrades to
`exec "$@"`. Each wrapper is guarded by a `command -v` check, so a missing binary
can never stop the game from starting. `gamemoderun` sits outside `gamescope`,
matching the configuration this design was derived from.

### Module layout

- `src-tauri/src/steam_vdf.rs`: VDF reading and editing, Tauri-free, unit tested
  on its own.
- `src-tauri/src/commands/wrapper.rs`: the commands `get_wrapper_status`,
  `install_hook` and `remove_hook`, plus script generation. Registered in
  `src-tauri/src/lib.rs`.
- `src-tauri/src/commands/config.rs`: the new `WrapperConfig`.
- `src/components/SettingsPage.tsx`: the Wrappers section.

## Configuration

`AppConfig` gains one nested struct, kept whole so it serialises and merges as a
unit and older configs deserialise with defaults intact (the existing
`config_round_trips_through_json_with_missing_fields` test covers that pattern):

```rust
pub struct WrapperConfig {
    pub gamemode: bool,                  // gamemoderun
    pub gamescope: bool,
    pub width: Option<u32>,              // -W
    pub height: Option<u32>,             // -H
    pub refresh: Option<u32>,            // -r
    pub display_mode: DisplayMode,       // Fullscreen (-f) | Borderless (-b) | Windowed
    pub force_grab_cursor: bool,         // --force-grab-cursor
    pub extra_args: String,              // free-form, appended to gamescope
    pub env: Vec<String>,                // "KEY=value" rows, exported before the wrappers
    pub previous_launch_options: Option<String>,
}
```

Everything defaults off, so upgrading DZL changes nobody's launch.

## Settings surface

A new `Section` titled **Wrappers**, next to the existing Launch section, holding:

- A status line for the hook: not installed, installed, or installed but changed
  outside DZL, with the Install or Reinstall button. Install is disabled with an
  explanation when neither `gamescope` nor `gamemode` is on `PATH`.
- Detection rows in the existing `StatusRow` style: GameMode found, gamescope
  found with its version. Reuses `binary_exists` and adds a `gamescope --version`
  read to `EnvironmentReport`.
- Toggles for GameMode and gamescope. The gamescope fields (resolution, refresh,
  display mode, force grab cursor, extra arguments) render only when gamescope is
  on, and each toggle is disabled when its binary is missing.
- The environment rows behind an "Advanced" disclosure, since almost nobody needs
  them. They exist so that importing an existing string such as `LD_PRELOAD=""`
  loses nothing.
- A live preview of the generated `exec` line, so what DZL will run is never a
  mystery.

Separately, the existing **Extra arguments** field gains an inline warning when a
value contains `%command%`, `gamescope`, `gamemoderun` or `mangohud`: those are
wrapper commands, DayZ receives them as literal arguments and ignores them, and
the Wrappers section is where they belong (MangoHud through `MANGOHUD=1` in the
environment rows). The warning does not block saving.

## Install, import and removal

Install is automatic with approval. DZL asks, closes Steam using the plumbing
that already exists for steamcmd (`shutdown_steam` and `start_steam`), writes the
hook, restarts Steam and confirms the value took.

Import runs as part of Install, reading the current `LaunchOptions` first:

- An empty value simply gets the hook.
- A non-empty value is parsed against a deliberately narrow grammar: leading
  `VAR=value` assignments, then optional `gamemoderun`, then optional
  `gamescope <flags> --`, then `%command%`, then any trailing arguments.
  Recognised gamescope flags are `-W`, `-H`, `-r`, `-f`, `-b` and
  `--force-grab-cursor`; unrecognised flags land in `extra_args` verbatim.
  Trailing arguments after `%command%` are appended to DZL's custom args, which
  is what they are.
- Anything the grammar cannot account for (`mangohud`, `sh -c`, `&&`, a
  user's own script) is not auto-imported. DZL shows the original string and asks
  whether to replace it.

The original value is stored as `previous_launch_options` either way, alongside
the file backup. Remove restores that value, or clears the entry when there was
none, over the same close-Steam-with-approval path, and deletes the script.

## Failure handling

- Writes happen only with Steam confirmed down. The command refuses if
  `steam_running()`.
- The edit is atomic: a temp file in the same directory, then a rename over the
  original, with `localconfig.vdf.dzl.bak` written first.
- If Steam will not shut down, or the file has no `apps` block, nothing is
  written and the error names the cause. In the shutdown case DZL shows the hook
  line with a copy button so the user is not stuck. This is error handling, not a
  second supported mode.
- Drift is reported, not silently repaired. `get_wrapper_status` compares Steam's
  stored value against the expected line, and `check_join_requirements` gains a
  `wrapper_hook_ok` flag so the join modal can warn when the settings ask for
  gamescope but the hook is gone. It never repairs mid-join, because that would
  mean closing Steam underneath the user.
- The script is regenerated in `run_join` as well as on save, so config and
  script cannot drift.

## Known scope change

Once the hook is installed, launching DayZ from Steam's own library also picks up
DZL's wrapper settings. This is intended and consistent, but it is a widening
from "DZL's launch options" and the Settings copy says so plainly.

## Testing

- `steam_vdf.rs`: replace an existing value; insert into an app block that has
  none; create the app block when DayZ was never launched; error when the `apps`
  block is missing; escape and unescape round trip (`LD_PRELOAD=""` stored as
  `\"\"`, and backslashes); tab indentation matched; the rest of the file
  preserved byte for byte; a second identical write changes nothing.
- Import parser: the real-world string from `localconfig.vdf` line 320 as a
  fixture; gamescope only; GameMode only; environment only; unknown flags into
  `extra_args`; trailing arguments into custom args; the refusal cases.
- Script generation: all off yields `exec "$@"`; each wrapper alone; both
  together; shell-quoting of values containing spaces; guards present.
- Config: a legacy config without `wrapper` deserialises with defaults.
- `ui.test.tsx`: the Wrappers section renders; gamescope fields appear only when
  enabled; disabled states when a binary is missing; the custom-args warning
  fires on all four keywords; the preview line matches the generated script.
- Manual: install the hook, join a server, and confirm `pgrep -af gamescope`
  shows the expected argv including `--force-grab-cursor`.

## Open question, out of scope

`--force-grab-cursor` appearing not to work on a DZL join is not an argument
problem: the log evidence shows the wrapper runs, and DZL never handles that flag
at all. The likely mechanism is focus, since gamescope holds the pointer only
while its own window is focused, and on a DZL join the launcher window is focused
when gamescope's window maps, then `hideToTrayOnLaunch` shuffles focus again as
the game appears. The manual test above settles whether the flag reaches
gamescope. Any focus fix is separate work.
